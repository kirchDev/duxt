Una extensión de duxt es una capa de Nuxt. Los componentes, los valores por defecto
de `app.config`, las rutas de servidor y los módulos ya viajan a través de
`extends`. Lo que Nuxt no puede transportar es todo lo que la compilación del
contenido tiene que saber: qué renderizador recibe una página, cómo un artefacto se
convierte en páginas y qué campos puede guardar una página. Eso va en un archivo
llamado `duxt.build.ts` en la raíz de la capa.

[ADR-0014](/adr/0014-load-integration-contributions-only-at-build-time) explica por
qué existe este archivo y por qué los analizadores nunca van en `app.config.ts`, que
se compila para el navegador.

## Escribir el archivo

```ts [duxt.build.ts]
import type { DuxtBuildContribution } from '@kirchdev/duxt/unstable';

export default {
  pageTypes: {
    recipe: { layout: 'recipe', template: 'RecipePage' }
  },
  pageSchema: (z) => ({
    servings: z.number().optional()
  })
} satisfies DuxtBuildContribution;
```

El archivo puede aportar cuatro cosas:

| Clave           | Qué añade                                                           |
| :-------------- | :------------------------------------------------------------------ |
| `pageTypes`     | Un layout y una plantilla, vinculados bajo un mismo nombre          |
| `sectionTypes`  | Un analizador de [sección generada](/concepts/generated-sections)   |
| `sourceFlavors` | Una forma de leer un dialecto de Markdown existente                 |
| `pageSchema`    | Campos de página, declarados con el `z` que Content pasa al callback |

Cada capa puede incluir uno. Se combinan a lo largo de `extends` y el sitio tiene
prioridad. Los mapas se reemplazan por entrada, de modo que un sitio sobrescribe un
tipo de página sin volver a declarar los demás.

::callout{type="warning"}
`@kirchdev/duxt/unstable` es la única exportación provisional. Su contenido puede
cambiar antes de que se fije el límite de extracción, así que fija la versión de duxt
con la que se compila una extensión.
::

## Añadir un tipo de página

Un tipo de página vincula un layout de Nuxt, que envuelve la página, con un
componente de plantilla, que dibuja el artículo. Incluye ambos en la capa:

```vue [app/components/RecipePage.vue]
<script setup lang="ts">
import type { DuxtPageTemplateProps } from '@duxt/utils/page-types';
defineProps<DuxtPageTemplateProps>();
</script>

<template>
  <article>
    <h1>{{ page.title }}</h1>
    <ContentRenderer :value="page" />
  </article>
</template>
```

El nombre de la plantilla debe estar en PascalCase y resolverse como un componente
global. La ruta ya ha cargado la página y se ha ocupado del SEO, por lo que una
plantilla solo recibe `page`, `untranslated` y `from`.

Selecciona el tipo para toda una fuente con `pageType` o para una sola página con
`type` en su frontmatter. La página tiene prioridad. Nombrar un tipo que nadie
registra hace fallar la compilación o la solicitud en lugar de recurrir a la
plantilla de documentación, porque un respaldo silencioso mostraría la página
equivocada.

## Saber qué necesita una imagen nueva

`duxt.build.ts` se ejecuta cuando se construye la imagen de la app. Añadir un tipo de
página, un analizador o un campo es un cambio de código, incluso en un sitio que
entrega sus páginas mediante
[bundles de contenido](/concepts/runtime-content-bundles). El contenido que los usa
puede viajar después en un bundle.

## Lista de comprobación

- [ ] `duxt.build.ts` está en la raíz de la capa y figura en `files` del paquete
- [ ] Ningún analizador ni esquema llega a `app.config.ts`
- [ ] El layout y la plantilla de cada tipo de página se incluyen en la capa
- [ ] Los campos se declaran mediante el `z` que recibe el callback
- [ ] El sitio compila con la capa únicamente en `extends`
