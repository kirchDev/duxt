Un paquete de contenido procesa las fuentes sin compilar Vite ni Nitro.
Construye el empaquetador desde el commit de la app para mantener el mismo
esquema, las colecciones y los componentes.
[ADR-0013](/adr/0013-load-content-bundles-at-runtime) explica el alcance Node y
SQLite; los despliegues habituales siguen reconstruyendo la app.

::callout{type="warning"}
Este comando solo produce un artefacto. Todavía no hace que un servidor en
marcha cargue o supervise bundles.
::

## Construir la app y el empaquetador juntos

`examples/content-bundles/Dockerfile` incluye los targets `app` y `packer`, que
comparten una etapa de fuentes y el lockfile. Desde la raíz del repositorio:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

La compilación escribe `.output/duxt-content-compat.json`. Extrae el archivo de
la imagen sin iniciar el servidor: contiene el hash de compatibilidad estructural
y los componentes detectados por Nuxt. Para otro sitio, ajusta el directorio de la
app y construye ambos targets desde el mismo checkout.

## Empaquetar un cambio de documentación

Modifica el Markdown del ejemplo y monta ese directorio en el empaquetador:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

En una app instalada, ejecuta `duxt content pack` desde la raíz de Nuxt. Procesa
las fuentes sin necesitar una compilación previa. Consulta las opciones y los
códigos de salida con `duxt content pack --help`. Imprime la ruta del bundle y
su hash. `--expect` lee el artefacto de la app y rechaza una estructura distinta
o componentes ausentes de la lista detectada por Nuxt antes de publicar. La
lista incluye actualmente componentes de UI y de layout; figurar en ella no
prueba que MDC pueda renderizar el componente desde un bundle. Alinear la lista
con el registro global de `app/components/content/` y probar un componente que
no se usó al compilar son tareas de
[#139](https://github.com/kirchDev/duxt/issues/139). Usar otros componentes de la
lista no cambia el hash estructural.

## Transferir el resultado completo

Un directorio de formato 1 se identifica por el SHA-256 de `SHA256SUMS`. Incluye
`bundle.json` con procedencia, compatibilidad y `usedComponents`, los `checksums`
de Content, sus dumps comprimidos sin cambios en `dumps/<collection>.txt`,
`redirects.json` y los archivos multimedia de documentación en `media/`. Los
hashes cubren todos los archivos de carga. La procedencia indica las versiones
de Content y duxt, y el commit cuando existen metadatos Git.

La publicación escribe y renombra primero el directorio completo; después
reemplaza atómicamente el archivo UTF-8 `current`, que contiene el identificador.
Ambas operaciones deben usar el mismo sistema de archivos. Sincroniza los
directorios inmutables antes de `current`; tu infraestructura se encarga del
transporte. Conserva los directorios anteriores mientras algún lector pueda usarlos.

El workflow `Content packer` construye los dos targets Docker, extrae el
artefacto, cambia Markdown y comprueba los hashes de un paquete compatible.

## Lista de comprobación

- [ ] Construir ambos targets con el commit y lockfile de la app.
- [ ] Extraer el artefacto de compatibilidad de la imagen de destino.
- [ ] Exigir `--expect` antes de publicar un cambio.
- [ ] Transferir los directorios completos antes de actualizar `current`.
