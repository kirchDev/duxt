Un paquete de contenido procesa las fuentes sin compilar Vite ni Nitro.
Construye el empaquetador desde el commit de la app para mantener el mismo
esquema, las colecciones y los componentes.
[ADR-0013](/adr/0013-load-content-bundles-at-runtime) explica el alcance Node y
SQLite; los despliegues habituales siguen reconstruyendo la app.

::callout{type="warning"}
Este comando solo produce un artefacto. Todavía no hace que un servidor en
marcha cargue o supervise bundles.
::

## Construir la app y el empaquetador juntos

`examples/content-bundles/Dockerfile` incluye los targets `app` y `packer`, que
comparten una etapa de fuentes y el lockfile. Desde la raíz del repositorio:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

La compilación escribe `.output/duxt-content-compat.json`. Extrae el archivo de
la imagen sin iniciar el servidor: contiene el hash de compatibilidad estructural
y los componentes MDC disponibles. Para otro sitio, ajusta el directorio de la
app y construye ambos targets desde el mismo checkout.

## Empaquetar un cambio de documentación

Modifica el Markdown del ejemplo y monta ese directorio en el empaquetador:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

En una app instalada, ejecuta `duxt content pack` desde la raíz de Nuxt. Procesa
las fuentes sin necesitar una compilación previa. Consulta las opciones y los
códigos de salida con `duxt content pack --help`. Imprime la ruta del bundle y
su hash. `--expect` lee el artefacto y rechaza una estructura distinta o componentes MDC
no disponibles antes de publicar. `availableComponents` incluye los componentes
de `app/components/content/` del consumidor y todas las capas, además de los ya
globales, como los de prosa de Content. Excluye componentes UI/de diseño sin usar
fuera de ese conjunto. Un componente puede aparecer por primera vez en un bundle
si su código ya estaba en un directorio de contenido de la imagen; cambiar el
subconjunto utilizado no cambia el hash estructural.

## Historial Git y búsqueda

Una fuente que lee historial necesita Git, un checkout válido y el historial
completo. Si falta o es superficial, el pack se detiene antes de publicar, incluso
con todas las páginas en caché. Un build normal solo avisa. Las fuentes locales
leen historial por defecto; `history: false` lo desactiva explícitamente.
Las remotas deben activarlo y completan su clon antes de leerlo.

El ejemplo Docker elige `history: false`: `.git` solo marca la raíz de las rutas
y no incluye Git ni historial. Para conservar fechas y colaboradores, proporciona
Git e historial completo en el target packer, sin metadatos de checkout en la app.

Tras publicar, [`duxt:search:records`](/reference/hooks) permite sincronizar al
proveedor instalado con claves de escritura solo en el packer. Si falla, el
comando falla y el bundle sigue publicado; repite el pack. El índice puede
adelantarse `pollSeconds` más la importación, o hasta el próximo pack válido
si el servidor rechaza el bundle.

## Transferir el resultado completo

Un directorio de formato 1 se identifica por el SHA-256 de `SHA256SUMS`. Incluye
`bundle.json` con procedencia, compatibilidad y `usedComponents`, los `checksums`
de Content, sus dumps comprimidos sin cambios en `dumps/<collection>.txt`,
`redirects.json` y los archivos multimedia de documentación en `media/`. Los
hashes cubren todos los archivos de carga. La procedencia indica las versiones
de Content y duxt, y el commit cuando existen metadatos Git.

La publicación escribe y renombra primero el directorio completo; después
reemplaza atómicamente el archivo UTF-8 `current`, que contiene el identificador.
Ambas operaciones deben usar el mismo sistema de archivos. Sincroniza los
directorios inmutables antes de `current`; tu infraestructura se encarga del
transporte. Conserva los directorios anteriores mientras algún lector pueda usarlos.

El workflow `Content packer` construye los dos targets Docker, extrae el
artefacto, cambia Markdown y comprueba los hashes de un paquete compatible.

## Activar la carga en ejecución

Construye un servidor Node de producción con SQLite en archivo. Desactiva el
prerenderizado de las páginas que deban cambiar: el HTML estático no sigue el
cambio de base de datos. Antes de construir aplicación y packer, por ejemplo:

```ts
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt'],
  routeRules: { '/**': { prerender: false } },
  nitro: { preset: 'node-server', prerender: { crawlLinks: false, routes: [] } },
  runtimeConfig: {
    duxt: { contentBundles: { pollSeconds: 30, statusRoute: false } },
  },
})
```

Una imagen construida sin variables de bundles puede activarlos al arrancar.
Para la aplicación Docker del ejemplo, configura **ambas variables antes de Node**:

```sh
docker run --rm -p 3000:3000 \
  -v "$PWD/publish:/content-bundles" \
  -e DUXT_CONTENT_BUNDLE_DIR=/content-bundles \
  -e 'NUXT_IPX_FS_DIR=["/content-bundles/active/media","/app/public"]' \
  docs-app
```

`NUXT_IPX_FS_DIR` incluye `active/media` y las raíces de imágenes habituales.
Añade otras raíces de tu sitio; `/app/public` corresponde a este Docker. Se
conserva IPX nativo. Si falta la raíz de medios, hay un aviso en logs y estado,
pero un bundle válido se activa igualmente.

La aplicación necesita crear/renombrar el enlace simbólico `active` en el montaje.
No crees `active` como directorio. Los directorios inmutables y `current` son del
operador; duxt gestiona el enlace. La alternativa a la variable corta es
`runtimeConfig.duxt.contentBundles.dir`. Sin directorio se sirve la imagen.

## Publicar, observar y recuperar

Transfiere directorios inmutables completos y sustituye `current` atómicamente
al final. El servidor comprueba al arrancar y luego consulta periódicamente;
no hace falta reiniciarlo. Un bundle ausente o inválido al inicio deja servir la
imagen; un rechazo posterior mantiene el activo. Publica la corrección con otro
identificador o apunta `current` a un bundle compatible conservado. Nunca edites
un directorio publicado.

Los logs estructurados `[duxt] content bundle` incluyen id, commit y motivo.
Opcionalmente, `contentBundles.statusRoute: true` en la configuración de ejecución
activa `GET /__duxt/content-bundle`, con `active`, `compatHash`, `lastRejection` y
`warnings` de IPX. Protege esa ruta en ingress o la red; está desactivada por
defecto y no es un endpoint de métricas.

Las réplicas cambian independientemente. Cuenta el intervalo de consulta, la
validación/importación y la espera de renderizados activos. Una recarga completa
aplica los nuevos checksums e invalida dumps viejos; una pestaña puede mantener
datos viejos durante navegación SPA. Redirecciones, medios, rutas MCP y cachés
OG/sitemap siguen la activación. Los índices externos se actualizan con
el hook `duxt:search:records` del pack. [Bundles en ejecución](/concepts/runtime-content-bundles) explica
estos límites, cuándo reconstruir la imagen y el transporte a cargo del operador.


## Lista de comprobación

- [ ] Construir ambos targets con el commit y lockfile de la app.
- [ ] Extraer el artefacto de compatibilidad de la imagen de destino.
- [ ] Exigir `--expect` antes de publicar un cambio.
- [ ] Transferir los directorios completos antes de actualizar `current`.

- [ ] Configurar ambas variables y permisos para el enlace.
- [ ] Proteger diagnósticos y prever réplicas, recargas e índices externos.
