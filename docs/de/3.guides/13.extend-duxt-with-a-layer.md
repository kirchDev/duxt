Eine duxt-Erweiterung ist eine Nuxt-Layer. Komponenten, `app.config`-Standardwerte,
Server-Routen und Module reisen bereits über `extends` mit. Was Nuxt nicht
transportieren kann, ist alles, was der Content-Build wissen muss: welchen Renderer
eine Seite bekommt, wie aus einem Artefakt Seiten werden und welche Felder eine
Seite speichern darf. Das gehört in eine Datei namens `duxt.build.ts` im Stamm
der Layer.

[ADR-0014](/adr/0014-load-integration-contributions-only-at-build-time) erklärt,
warum es diese Datei gibt und warum Parser nie in `app.config.ts` gehören, das in
den Browser kompiliert wird.

## Die Datei schreiben

```ts [duxt.build.ts]
import type { DuxtBuildContribution } from '@kirchdev/duxt/unstable';

export default {
  pageTypes: {
    recipe: { layout: 'recipe', template: 'RecipePage' }
  },
  pageSchema: (z) => ({
    servings: z.number().optional()
  })
} satisfies DuxtBuildContribution;
```

Die Datei kann vier Dinge beitragen:

| Schlüssel       | Was er hinzufügt                                                    |
| :-------------- | :------------------------------------------------------------------ |
| `pageTypes`     | Ein Layout und ein Template, unter einem Namen gebunden             |
| `sectionTypes`  | Einen Parser für eine [generierte Sektion](/concepts/generated-sections) |
| `sourceFlavors` | Eine Möglichkeit, einen vorhandenen Markdown-Dialekt zu lesen       |
| `pageSchema`    | Seitenfelder, deklariert mit dem `z`, das Content dem Callback übergibt |

Jede Layer darf eine solche Datei mitbringen. Sie werden über `extends` hinweg
zusammengeführt, und die Site hat Vorrang. Maps werden pro Eintrag ersetzt, sodass
eine Site einen Seitentyp überschreiben kann, ohne die anderen erneut anzugeben.

::callout{type="warning"}
`@kirchdev/duxt/unstable` ist der einzige provisorische Export. Sein Inhalt kann sich
ändern, bevor die Extraktionsgrenze feststeht. Pinne deshalb die duxt-Version, gegen
die eine Erweiterung gebaut wird.
::

## Einen Seitentyp hinzufügen

Ein Seitentyp bindet ein Nuxt-Layout, das die Seite umschließt, an eine
Template-Komponente, die den Artikel zeichnet. Liefere beide in der Layer aus:

```vue [app/components/RecipePage.vue]
<script setup lang="ts">
import type { DuxtPageTemplateProps } from '@duxt/utils/page-types';
defineProps<DuxtPageTemplateProps>();
</script>

<template>
  <article>
    <h1>{{ page.title }}</h1>
    <ContentRenderer :value="page" />
  </article>
</template>
```

Der Template-Name muss in PascalCase geschrieben sein und sich als globale
Komponente auflösen lassen. Die Route hat die Seite bereits geladen und sich um SEO
gekümmert, deshalb erhält ein Template nur `page`, `untranslated` und `from`.

Wähle den Typ mit `pageType` für eine ganze Quelle oder mit `type` im Frontmatter
für eine einzelne Seite. Die Seite hat Vorrang. Ein Typ, den niemand registriert,
lässt den Build oder die Anfrage fehlschlagen, statt auf das Doku-Template
zurückzufallen, denn ein stiller Fallback würde die falsche Seite anzeigen.

## Wissen, was ein neues Image braucht

`duxt.build.ts` läuft, wenn das App-Image gebaut wird. Einen Seitentyp, einen Parser
oder ein Feld hinzuzufügen ist eine Codeänderung, auch auf einer Site, die ihre
Seiten über [Content-Bundles](/concepts/runtime-content-bundles) ausliefert. Die
Inhalte, die sie verwenden, können danach in einem Bundle reisen.

## Checkliste

- [ ] `duxt.build.ts` liegt im Stamm der Layer und steht in den `files` des Pakets
- [ ] Weder Parser noch Schema gelangen nach `app.config.ts`
- [ ] Layout und Template jedes Seitentyps werden in der Layer ausgeliefert
- [ ] Felder werden über das `z` deklariert, das der Callback erhält
- [ ] Die Site baut, wenn die Layer nur in `extends` steht
