Ein Content-Pack liest die Quellen ein, ohne Vite oder Nitro zu kompilieren.
Erzeuge den Packer aus demselben Commit wie die App, damit Schema, Collections
und Komponenten übereinstimmen. [ADR-0013](/adr/0013-load-content-bundles-at-runtime)
beschreibt den Geltungsbereich Node und SQLite; normale Deployments bauen die App neu.

::callout{type="warning"}
Dieser Befehl erstellt nur ein Artefakt. Ein laufender Server lädt oder überwacht
dadurch noch keine Bundles.
::

## App und Packer zusammen bauen

`examples/content-bundles/Dockerfile` enthält die Targets `app` und `packer` mit
einer gemeinsamen Quellstufe und einem Lockfile. Im Repository-Stamm ausführen:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

Der App-Build schreibt `.output/duxt-content-compat.json`. Lies die Datei ohne
Serverstart aus dem Image; sie enthält den strukturellen Kompatibilitätshash und
die verfügbaren MDC-Komponenten. Passe für eine eigene Website das
Consumer-Verzeichnis an und baue beide Targets aus demselben Checkout.

## Eine Dokumentationsänderung packen

Ändere das Markdown des Beispiels und mounte dieses Verzeichnis im Packer:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

In einer installierten Consumer-App läuft `duxt content pack` im Nuxt-Stamm.
Der Befehl parst die Quellen ohne vorherigen Build. `duxt content pack --help`
zeigt Optionen und Exitcodes. Die Ausgabe enthält Bundle-Pfad und Hash.
`--expect` liest das App-Artefakt und lehnt vor Veröffentlichung eine andere
Struktur oder nicht verfügbare MDC-Komponenten ab. `availableComponents` enthält
`app/components/content/` des Consumers und aller Layer sowie bereits globale
Komponenten, etwa Contents Prose-Komponenten. Unbenutzte UI-/Layout-Komponenten
außerhalb dieser Menge sind ausgeschlossen. Ein Bundle darf eine bisher
unbenutzte Komponente verwenden, wenn ihr Code bereits im Content-Verzeichnis
des Images liegt. Eine andere Teilmenge ändert den strukturellen Hash nicht.

## Git-Historie und Suche

Eine Quelle mit Historie braucht Git, einen gültigen Checkout und vollständige
Historie. Fehlende oder flache Historie stoppt den Pack vor der Veröffentlichung,
auch bei vollständig gefülltem Parse-Cache. Normale Builds warnen stattdessen.
Lokale Quellen lesen standardmäßig Historie; `history: false` schaltet das
ausdrücklich aus. Entfernte Quellen müssen sie anfordern und werden vorher vervollständigt.

Das Docker-Beispiel setzt bewusst `history: false`: `.git` markiert dort nur
die Pfadwurzel; Git und Checkout-Historie fehlen. Für Seitendaten und Contributor
im eigenen Packer müssen Git und vollständige Historie in dessen Target liegen,
während das App-Target keine Checkout-Metadaten enthält.

Nach der Veröffentlichung synchronisiert ein installierter Anbieter über
[`duxt:search:records`](/reference/hooks) mit Schreibschlüsseln nur im Packer.
Ein Sync-Fehler beendet den Befehl mit Fehler, lässt das Bundle aber veröffentlicht;
den Pack zum Wiederholen erneut ausführen. Der Index kann um `pollSeconds` plus
Importzeit vorauslaufen; ein abgelehntes Bundle lässt ihn bis zum nächsten gültigen Pack voraus.

## Das vollständige Ergebnis übertragen

Ein Verzeichnis mit Format 1 heißt nach dem SHA-256 seiner Datei `SHA256SUMS`.
Es enthält `bundle.json` mit Herkunft, Kompatibilität und `usedComponents`,
Contents `checksums`, unveränderte komprimierte Dumps unter
`dumps/<collection>.txt`, `redirects.json` und Dokumentationsdateien unter
`media/`. Die Hashes decken alle Nutzdateien ab. Die Herkunft enthält Content-
und duxt-Version sowie den Commit, falls Git-Metadaten vorliegen.

Die Veröffentlichung schreibt zuerst das vollständige Verzeichnis und benennt
es um. Erst danach ersetzt sie atomar die UTF-8-Datei `current` mit der Kennung.
Beide Schritte brauchen dasselbe Dateisystem. Übertrage unveränderliche
Verzeichnisse vor `current`; der Transport gehört zur Deployment-Infrastruktur.
Bewahre alte Verzeichnisse auf, solange Leser sie noch verwenden könnten.

Der Workflow `Content packer` baut beide Docker-Targets, liest das App-Artefakt,
ändert Markdown und prüft die Dateihashes eines kompatiblen Packs.

## Laden zur Laufzeit aktivieren

Baue einen produktiven Node-Server mit dateibasierter SQLite-Datenbank.
Deaktiviere Prerendering für veränderliche Seiten: Statisches HTML folgt keinem
Datenbankwechsel. Vor dem Build von App und Packer zum Beispiel:

```ts
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt'],
  routeRules: { '/**': { prerender: false } },
  nitro: { preset: 'node-server', prerender: { crawlLinks: false, routes: [] } },
  runtimeConfig: {
    duxt: { contentBundles: { pollSeconds: 30, statusRoute: false } },
  },
})
```

Ein Image ohne Bundle-Umgebungsvariablen beim Build kann beim Prozessstart
aktiviert werden. Für das mitgelieferte Docker-Layout **beide Variablen vor Node setzen**:

```sh
docker run --rm -p 3000:3000 \
  -v "$PWD/publish:/content-bundles" \
  -e DUXT_CONTENT_BUNDLE_DIR=/content-bundles \
  -e 'NUXT_IPX_FS_DIR=["/content-bundles/active/media","/app/public"]' \
  docs-app
```

`NUXT_IPX_FS_DIR` enthält den verwalteten Pfad `active/media` und die normalen
Bildwurzeln. Ergänze weitere Wurzeln deiner Website; `/app/public` gehört zu
diesem Docker-Layout. Der native IPX-Handler bleibt erhalten. Fehlende
Medienwurzel erzeugt eine Warnung in Logs und Status, verhindert aber keine Aktivierung.

Die App braucht Schreibrechte zum Erstellen/Umbenennen des `active`-Symlinks im
Mount. Lege `active` nicht als Verzeichnis an. Unveränderliche Nutzverzeichnisse
und `current` gehören dem Betreiber; der Symlink gehört duxt. Alternativ zum
kurzen Verzeichnis-Variablennamen gilt `runtimeConfig.duxt.contentBundles.dir`.
Ohne Verzeichnis bleibt der Image-Inhalt aktiv.

## Veröffentlichen, beobachten und wiederherstellen

Übertrage vollständige unveränderliche Verzeichnisse, ersetze danach `current`
atomar. Der Server prüft beim Start und pollt anschließend; kein Neustart ist
nötig. Ein fehlendes/ungültiges Start-Bundle führt zum Image-Inhalt; spätere
Ablehnungen behalten das aktive Bundle. Veröffentliche eine korrigierte neue
Kennung oder setze `current` auf ein aufbewahrtes kompatibles Bundle. Bearbeite
veröffentlichte Verzeichnisse niemals nachträglich.

Strukturierte `[duxt] content bundle`-Logs nennen Kennung, Commit und Grund.
Optional aktiviert `contentBundles.statusRoute: true` in der Laufzeitkonfiguration
`GET /__duxt/content-bundle` mit `active`, `compatHash`, `lastRejection` und
IPX-`warnings`. Schütze die Route am Ingress oder an der Netzwerkgrenze. Sie ist
standardmäßig aus und kein Metrikendpunkt.

Jedes Replikat schaltet unabhängig. Plane Pollintervall, Prüfung/Import und das
Beenden laufender Renderings ein. Vollständiges Neuladen übernimmt neue
Prüfsummen und verwirft alte Content-Dumps; offene Tabs können bei SPA-Navigation
alten Inhalt behalten. Weiterleitungen, Medien, MCP-Pfade, OG- und Sitemap-Caches
folgen der Aktivierung. Externe Suchindizes werden über den Pack-Hook `duxt:search:records` aktualisiert.
[Content-Bundles zur Laufzeit](/concepts/runtime-content-bundles) beschreibt diese
Grenzen, notwendige Image-Neubauten und den Transport als Betreiberaufgabe.
