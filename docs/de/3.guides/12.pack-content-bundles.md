Ein Content-Pack liest die Quellen ein, ohne Vite oder Nitro zu kompilieren.
Erzeuge den Packer aus demselben Commit wie die App, damit Schema, Collections
und Komponenten übereinstimmen. [ADR-0013](/adr/0013-load-content-bundles-at-runtime)
beschreibt den Geltungsbereich Node und SQLite; normale Deployments bauen die App neu.

::callout{type="warning"}
Dieser Befehl erstellt nur ein Artefakt. Ein laufender Server lädt oder überwacht
dadurch noch keine Bundles.
::

## App und Packer zusammen bauen

`examples/content-bundles/Dockerfile` enthält die Targets `app` und `packer` mit
einer gemeinsamen Quellstufe und einem Lockfile. Im Repository-Stamm ausführen:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

Der App-Build schreibt `.output/duxt-content-compat.json`. Lies die Datei ohne
Serverstart aus dem Image; sie enthält den strukturellen Kompatibilitätshash und
die verfügbaren MDC-Komponenten. Passe für eine eigene Website das
Consumer-Verzeichnis an und baue beide Targets aus demselben Checkout.

## Eine Dokumentationsänderung packen

Ändere das Markdown des Beispiels und mounte dieses Verzeichnis im Packer:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

In einer installierten Consumer-App läuft `duxt content pack` im Nuxt-Stamm.
Der Befehl parst die Quellen ohne vorherigen Build. `duxt content pack --help`
zeigt Optionen und Exitcodes. Die Ausgabe enthält Bundle-Pfad und Hash.
`--expect` liest das App-Artefakt und lehnt vor der Veröffentlichung eine andere
Struktur oder im Image fehlende Komponenten ab. Andere bereits vorhandene
Komponenten zu verwenden ändert den strukturellen Hash nicht.

## Das vollständige Ergebnis übertragen

Ein Verzeichnis mit Format 1 heißt nach dem SHA-256 seiner Datei `SHA256SUMS`.
Es enthält `bundle.json` mit Herkunft, Kompatibilität und `usedComponents`,
Contents `checksums`, unveränderte komprimierte Dumps unter
`dumps/<collection>.txt`, `redirects.json` und Dokumentationsdateien unter
`media/`. Die Hashes decken alle Nutzdateien ab. Die Herkunft enthält Content-
und duxt-Version sowie den Commit, falls Git-Metadaten vorliegen.

Die Veröffentlichung schreibt zuerst das vollständige Verzeichnis und benennt
es um. Erst danach ersetzt sie atomar die UTF-8-Datei `current` mit der Kennung.
Beide Schritte brauchen dasselbe Dateisystem. Übertrage unveränderliche
Verzeichnisse vor `current`; der Transport gehört zur Deployment-Infrastruktur.
Bewahre alte Verzeichnisse auf, solange Leser sie noch verwenden könnten.

Der Workflow `Content packer` baut beide Docker-Targets, liest das App-Artefakt,
ändert Markdown und prüft die Dateihashes eines kompatiblen Packs.

## Checkliste

- [ ] Beide Targets aus App-Commit und Lockfile bauen.
- [ ] Das Kompatibilitätsartefakt aus dem Ziel-Image auslesen.
- [ ] Vor Veröffentlichung `--expect` verlangen.
- [ ] Vollständige Verzeichnisse vor `current` übertragen.
