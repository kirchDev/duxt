`@kirchdev/duxt-wiki` rendert eine Quelle als Wiki statt als Dokumentation: Der
Artikel nutzt die volle Breite, das Inhaltsverzeichnis wandert in den Text, und
Seiten verlinken einander über ihren Namen. Die Seiten bleiben Markdown in Git.
Die Layer bringt weder Browser-Editor noch Konten oder Kommentare mit. In der
[Wiki-Demo](https://duxt.app/demo/wiki) siehst du sie in Aktion.

## Die Layer hinzufügen

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt', '@kirchdev/duxt-wiki']
})
```

Gib einer Quelle anschließend den Seitentyp `article`:

```ts [app/app.config.ts]
export default defineAppConfig({
  duxt: {
    sources: [
      { path: 'wiki', slug: 'wiki', pageType: 'article' }
    ]
  }
})
```

::callout{type="warning"}
Die Layer ergänzt Content-Spalten, Komponenten und Seitentypen, deshalb braucht
ihre Installation einmalig ein neues App-Image. Danach sind Seiten, Aliase,
Kategorien und neue Infobox-Felder Inhaltsänderungen. Sie können einen laufenden
Node-Server über [Content-Bundles](/concepts/runtime-content-bundles) erreichen.
::

## Seitentypen

Der `pageType` einer Quelle gilt für alle ihre Seiten. Eine Seite überschreibt ihn
mit `type` in ihrem Frontmatter.

| Typ              | Verwendet für                                                       |
| :--------------- | :------------------------------------------------------------------ |
| `article`        | Eine gewöhnliche Seite, mit der Gliederung nach dem Einleitungsabsatz |
| `category`       | Eine Seite, die eine Kategorie vorstellt und ihre Mitglieder auflistet |
| `disambiguation` | Eine Seite, die von einem gemeinsamen Titel auf seine verschiedenen Bedeutungen verweist |

Die linke Navigation ist ausgeschaltet, weil man ein Wiki über seine Links liest.
Mit `wiki: { sidebar: true }` in `app.config.ts` schaltest du sie für die gesamte
Site wieder ein.

## Über Namen verlinken

`[[Target]]` verlinkt eine Seite über ihren Titel, einen ihrer Aliase oder ihren
Pfad. Der Link wird beim Rendern der Seite aufgelöst, sodass du nach dem Umbenennen
eines Ziels die darauf verweisenden Seiten nicht anpassen musst.

```md
[[Crown Light]]
[[Crown Light|the outer beacon]]
[[Crown Light#History]]
[[guides/mooring]]
[[~/other-source/Harbour map]]
```

Bei Namen spielt die Groß- und Kleinschreibung keine Rolle. Ein Link sucht in seiner
eigenen Quelle und Version und danach in den Sprach-Fallbacks dieser Quelle. Ein
vorangestelltes `~/` verlässt diesen Bereich ausdrücklich. Inline-Code und
Codeblöcke bleiben unverändert.

Weitere Namen gibst du einer Seite mit `aliases: [Outer Light]` in ihrem
Frontmatter. Passt ein Name auf mehrere Seiten, gewinnt eine `disambiguation`-Seite
mit diesem Titel. Ohne eine solche Seite bleibt der Link rot und der Build warnt,
denn Raten würde Leser auf die falsche Seite schicken.

## Rote Links und Backlinks

Ein Link auf eine nicht vorhandene Seite wird rot dargestellt und lässt den Build
nie fehlschlagen. Er öffnet die Seite `/wanted?title=…` der Quelle, die erklärt,
dass die Seite fehlt, und auflistet, wer darauf verlinkt. Auf einer erkannten Forge
bietet diese Seite einen vorausgefüllten Vorschlag zum Anlegen der Datei an, sodass
auch das Schreiben weiterhin über Git läuft. `/wanted` ohne Titel listet alle
fehlenden Seiten auf.

Jeder Artikel endet mit den Seiten, die auf ihn verlinken. Einfache
Markdown-Downloads, MCP und `llms-full.txt` erhalten gewöhnliche Links, und ein
nicht aufgelöster Name wird zu einfachem Text, sodass ein maschineller Leser nie
`[[…]]` sieht.

## Kategorien und Navboxen

Liste die Kategorien einer Seite in ihrem Frontmatter auf:

```md
---
title: Crown Light
categories: [Beacons]
---
```

Kategorieseiten liegen unter `<source>/category/<name>`, und die eigenen
`categories` einer Seite sind ihre Eltern. Eine Kategorie mit Mitgliedern
funktioniert auch ohne eigene Seite. Schreibe eine mit `type: category`, wenn sie
eine Einleitung braucht.

Eine Navbox stellt eine Kategorie und ihre Unterkategorien als Linkblock dar. Sie
erscheint nur dort, wo du sie platzierst:

```mdc
::navbox{category="Beacons"}
::
```

## Infoboxen und Abfragen

Setze eine Infobox an den Anfang des Artikeltexts, vor die Einleitung. Auf einem
breiten Bildschirm fließt sie neben dem Text, auf einem Smartphone steht sie darüber.

```mdc
::infobox{title="Crown Light" image="/crown.svg" type="beacon"}
:::infobox-row{label="Status" key="status"}
Lit
:::
:::infobox-group{title="Visit" collapsed}
::::infobox-row{label="Base" key="base"}
[[Lumen Harbour]]
::::
:::
::
```

Zeilen dürfen Markdown und Wikilinks enthalten. Der Build speichert außerdem den
reinen Text jeder Zeile als Seitendaten, unter ihrem `key` oder, wenn keiner gesetzt
ist, unter ihrem Label. Setze bei jeder Zeile mit übersetztem Label einen `key`,
damit jede Sprache dasselbe Feld speichert.

`::query` listet Seiten anhand dieser Daten auf, in der aktuellen Quelle und Version:

```mdc
::query{type="beacon" where="status=Lit" columns="title,base"}
::
```

`where` vergleicht ein `key=value` als Text mit Beachtung der Groß- und
Kleinschreibung, daher unterscheiden sich `01` und `1`. `columns` ist standardmäßig
`title`, das auf die Seite verlinkt.

## Finden, was Aufmerksamkeit braucht

[`duxt report`](/reference/cli) ergänzt seine Ausgabe um gewünschte, verwaiste,
Sackgassen- und nicht kategorisierte Seiten.

## Checkliste

- [ ] `@kirchdev/duxt-wiki` steht in `extends` nach `@kirchdev/duxt`
- [ ] Die Quelle nennt `pageType: 'article'`
- [ ] Nach der Installation der Layer wurde ein neues App-Image gebaut
- [ ] Titel, die sich mehrere Seiten teilen, haben eine `disambiguation`-Seite
- [ ] Zeilen mit übersetzten Labels tragen einen `key`
- [ ] `duxt report` zeigt keine gewünschte Seite, die du eigentlich schreiben wolltest
