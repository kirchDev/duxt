---
title: Several languages
description: Pick which of the layer's locales your site serves, and translate the strings you configured.
icon: lucide:languages
---

The theme's own strings are translated in seven locales. A site serves the subset
it wants and translates the strings it configured itself. The Markdown is a
separate question — see [What is not translated](#what-is-not-translated) below.

## Steps

::steps
1. **Narrow the list with `duxt.locales`.**

   ```ts [app/app.config.ts]
   locales: ['en-GB', 'de-DE']
   ```

   Not i18n's own `locales` array: that one merges across layers instead of
   replacing, so declaring two there leaves the other five routed and announced
   in `hreflang`.

2. **Pick the unprefixed one** in `nuxt.config.ts` with `i18n.defaultLocale`.
   It is URL-relevant: changing it later moves every page in both directions at
   once.

3. **Translate your own strings.** For a handful, the record form costs less than
   a locale file per language:

   ```ts
   sections: [
     {
       label: { 'en-GB': 'Guides', 'de-DE': 'Anleitungen' },
       to: '/guides',
       icon: 'lucide:book-open'
     }
   ]
   ```

   For more than a handful, register your own i18n keys and write the key. Do not
   reach for `duxt.defaults.*` — those are the layer's internal keys, and a
   rename there would break your site silently.

4. **Set the origin.** `hreflang` is not valid relative, so it needs
   `i18n.baseUrl` or `NUXT_PUBLIC_I18N_BASE_URL`.

5. **Open a page under each locale** and check that the chrome changed language,
   the path still resolves, and no configured label prints as a raw key.
::

## What is not translated

The Markdown itself. `useDuxtPath()` strips the locale segment before every
content lookup, so `/de-DE/guides/deploying` and `/guides/deploying` resolve to
the same file: the interface around the page changes language, the page does not.

::callout{type="warning" title="One content tree, every locale"}
A translated `docs/` tree is not read. Content has no notion of a locale, and the
layer generates one collection per source and version — not one per language.
Serving translated pages would need a collection per locale, which the source
list cannot express today.
::

A site that needs translated documentation today has one workable route: publish
each language as its own site, with its own `docs/` tree and its own
`i18n.defaultLocale`.

## Checklist

- [ ] `duxt.locales` lists exactly the locales you serve
- [ ] `/sitemap.xml` contains one entry per page per locale, and no others
- [ ] `hreflang` links are absolute
- [ ] No configured label prints as a raw key
- [ ] Switching locale keeps the reader on the same page
