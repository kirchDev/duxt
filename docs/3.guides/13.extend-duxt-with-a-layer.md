title: Extend duxt with a layer
description: Add page types, generated sections, source flavours and page fields from a Nuxt layer with one build-only file.

---

A duxt extension is a Nuxt layer. Components, `app.config` defaults, server routes
and modules already travel through `extends`. What Nuxt cannot carry is anything
the content build has to know: which renderer a page gets, how an artefact becomes
pages, and which fields a page may store. Those go in a file named `duxt.build.ts`
at the root of the layer.

[ADR-0014](/adr/0014-load-integration-contributions-only-at-build-time) explains why
this file exists and why parsers never go in `app.config.ts`, which is compiled
into the browser.

## Write the file

```ts [duxt.build.ts]
import type { DuxtBuildContribution } from '@kirchdev/duxt/unstable';

export default {
  pageTypes: {
    recipe: { layout: 'recipe', template: 'RecipePage' }
  },
  pageSchema: (z) => ({
    servings: z.number().optional()
  })
} satisfies DuxtBuildContribution;
```

The file can contribute four things:

| Key             | What it adds                                                        |
| :-------------- | :------------------------------------------------------------------ |
| `pageTypes`     | A layout and a template, bound under one name                       |
| `sectionTypes`  | A [generated section](/concepts/generated-sections) parser           |
| `sourceFlavors` | A way to read an existing Markdown dialect                          |
| `pageSchema`    | Page fields, declared with the `z` that Content hands to the callback |

Every layer may ship one. They merge across `extends`, and the site wins. Maps
replace by entry, so a site overrides one page type without restating the others.

::callout{type="warning"}
`@kirchdev/duxt/unstable` is the one provisional export. Its contents may change
before the extraction boundary is settled, so pin the version of duxt an extension
is built against.
::

## Add a page type

A page type binds a Nuxt layout, which wraps the page, to a template component,
which draws the article. Ship both in the layer:

```vue [app/components/RecipePage.vue]
<script setup lang="ts">
import type { DuxtPageTemplateProps } from '@duxt/utils/page-types';
defineProps<DuxtPageTemplateProps>();
</script>

<template>
  <article>
    <h1>{{ page.title }}</h1>
    <ContentRenderer :value="page" />
  </article>
</template>
```

The template name has to be PascalCase and resolve as a global component. The
route has already loaded the page and handled SEO, so a template only receives
`page`, `untranslated` and `from`.

Select the type for a whole source with `pageType`, or for one page with `type` in
its frontmatter. The page wins. Naming a type that nothing registers fails the
build or the request rather than falling back to the docs template, because a
silent fallback would show the wrong page.

## Know what needs a new image

`duxt.build.ts` runs when the application image is built. Adding a page type, a
parser or a field is a code change, even on a site that delivers its pages through
[content bundles](/concepts/runtime-content-bundles). The content that uses them
can travel in a bundle afterwards.

## Checklist

- [ ] `duxt.build.ts` sits at the root of the layer and is listed in the package's `files`
- [ ] No parser or schema reaches `app.config.ts`
- [ ] Each page type's layout and template ship in the layer
- [ ] Fields are declared through the `z` the callback receives
- [ ] The site builds with the layer only in `extends`
