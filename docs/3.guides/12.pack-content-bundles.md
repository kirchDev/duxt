A content pack parses the sources without compiling Vite or Nitro. Build the
packer from the app's commit so its schema, collections and component code
agree. [ADR-0013](/adr/0013-load-content-bundles-at-runtime) explains the
Node and SQLite scope; ordinary deployments still rebuild their app.

::callout{type="warning"}
This command produces an artefact only. It does not make a running server load
or watch bundles.
::

## Build the app and packer together

The repository's `examples/content-bundles/Dockerfile` has `app` and `packer`
targets sharing one source stage and lockfile. From the repository root:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

The app build writes `.output/duxt-content-compat.json`. Extract it without
starting the app; the file names its structural compatibility hash and scanned
Nuxt components. For your own site, keep the same two targets and adjust the
consumer directory. Build both from the same checkout.

## Pack a documentation change

Update the example's Markdown, then mount that directory into the packer:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

For an installed consumer, run `duxt content pack` from its Nuxt root. It parses
fresh sources without requiring an earlier build. Use `duxt content pack --help`
for the options and exit codes. The command prints the bundle path and
compatibility hash; `--expect` reads the app artefact and rejects a different
structure or a component absent from the scanned Nuxt component list before
publication. The list currently includes UI and layout components; membership
does not prove MDC can render one from a bundle. Aligning it with global
`app/components/content/` registration and testing an initially unused component
are tracked in [#139](https://github.com/kirchDev/duxt/issues/139). Changing which
listed components the content uses does not change the structural hash.

## Transport the complete result

A format-1 directory is named by the SHA-256 of its `SHA256SUMS` file. It contains
`bundle.json` with provenance, compatibility and `usedComponents`, Content's
`checksums`, its unchanged compressed dumps in `dumps/<collection>.txt`,
`redirects.json` and documentation `media/`. File hashes cover every payload
file. Provenance records the Content and duxt versions, plus the checkout commit
when Git metadata is present.

Publication writes and renames the complete directory first, then atomically
replaces the UTF-8 `current` file containing its identifier. Keep both operations
on one filesystem. Sync immutable directories before syncing `current`; storage
transport belongs to your deployment tooling. Retain an old directory while any
reader may still use it.

The `Content packer` workflow builds both Docker targets, reads the image
artefact, changes Markdown and verifies a compatible pack's file hashes.

## Checklist

- [ ] Build both targets from the app's commit and lockfile.
- [ ] Extract the compatibility artefact from the image being targeted.
- [ ] Require `--expect` before publishing a content change.
- [ ] Transfer complete immutable directories before updating `current`.
