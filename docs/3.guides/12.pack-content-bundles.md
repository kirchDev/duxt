A content pack parses the sources without compiling Vite or Nitro. Build the
packer from the app's commit so its schema, collections and component code
agree. [ADR-0013](/adr/0013-load-content-bundles-at-runtime) explains the
Node and SQLite scope; ordinary deployments still rebuild their app.

::callout{type="warning"}
This command produces an artefact only. It does not make a running server load
or watch bundles.
::

## Build the app and packer together

The repository's `examples/content-bundles/Dockerfile` has `app` and `packer`
targets sharing one source stage and lockfile. From the repository root:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

The app build writes `.output/duxt-content-compat.json`. Extract it without
starting the app; the file names its structural compatibility hash and available
MDC components. For your own site, keep the same two targets and adjust the
consumer directory. Build both from the same checkout.

## Pack a documentation change

Update the example's Markdown, then mount that directory into the packer:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

For an installed consumer, run `duxt content pack` from its Nuxt root. It parses
fresh sources without requiring an earlier build. Use `duxt content pack --help`
for the options and exit codes. The command prints the bundle path and
compatibility hash; `--expect` reads the app artefact and rejects a different structure or an
unavailable MDC component before publication. `availableComponents` covers the
consumer's and all layers' `app/components/content/` components, plus already
global components such as Content's prose components. Unused UI/layout components
outside that set are excluded. A component may first appear in a runtime bundle
if its code already shipped in a content directory; changing the subset used by
content does not change the structural hash.

## Git history and search

A source that reads history needs Git, a valid checkout and its complete
history. A missing or shallow history stops the pack before publication, even
when every page was already cached. Ordinary builds warn instead. Local
sources read history by default; `history: false` disables it explicitly.
Remote history remains opt-in and its clone is deepened before reading it.

The Docker example deliberately sets `history: false`: its `.git` directory is
only a path-root marker, and it ships neither Git nor checkout history. To keep
page dates and contributors in your own packer, provide Git and full history in
the packer target, keeping checkout metadata out of the app target.

After publication, [`duxt:search:records`](/reference/hooks) lets an installed
provider sync the index using write keys available only in the packer. A failed
sync fails the command but keeps the published bundle, so retry the pack. The
index can lead content by `pollSeconds` plus import time; a rejected bundle
leaves it ahead until the next good pack.

## Transport the complete result

A format-1 directory is named by the SHA-256 of its `SHA256SUMS` file. It contains
`bundle.json` with provenance, compatibility and `usedComponents`, Content's
`checksums`, its unchanged compressed dumps in `dumps/<collection>.txt`,
`redirects.json` and documentation `media/`. File hashes cover every payload
file. Provenance records the Content and duxt versions, plus the checkout commit
when Git metadata is present.

Publication writes and renames the complete directory first, then atomically
replaces the UTF-8 `current` file containing its identifier. Keep both operations
on one filesystem. Sync immutable directories before syncing `current`; storage
transport belongs to your deployment tooling. Retain an old directory while any
reader may still use it.

The `Content packer` workflow builds both Docker targets, reads the image
artefact, changes Markdown and verifies a compatible pack's file hashes.

## Enable runtime loading

Build a production Node server with file-backed SQLite. Disable prerendering for
the pages you want to change; a static HTML file cannot follow a database switch.
For example, before building the app and packer:

```ts
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt'],
  routeRules: { '/**': { prerender: false } },
  nitro: { preset: 'node-server', prerender: { crawlLinks: false, routes: [] } },
  runtimeConfig: {
    duxt: { contentBundles: { pollSeconds: 30, statusRoute: false } },
  },
})
```

An image built without bundle environment settings can opt in at process start.
For the shipped Docker app, set **both variables before starting Node**:

```sh
docker run --rm -p 3000:3000 \
  -v "$PWD/publish:/content-bundles" \
  -e DUXT_CONTENT_BUNDLE_DIR=/content-bundles \
  -e 'NUXT_IPX_FS_DIR=["/content-bundles/active/media","/app/public"]' \
  docs-app
```

`NUXT_IPX_FS_DIR` includes the managed `active/media` path and ordinary image roots.
Add any other roots your site uses; `/app/public` matches this Docker layout.
Keep the native IPX handler. Missing media-root wiring logs a warning and appears
in status diagnostics, but a valid bundle still activates.

The app must be allowed to create/rename the `active` symlink in the bundle
mount. Do not pre-create `active` as a directory. The operator owns immutable
payload directories and `current`; duxt owns that symlink. The short directory
variable also has the configuration equivalent
`runtimeConfig.duxt.contentBundles.dir`. Unset means ordinary image content.

## Publish, observe and recover

Transfer full immutable directories, then replace `current` atomically. The
server checks at startup and polls thereafter; no restart is needed. A missing or
invalid startup bundle serves the image; a later rejection retains the active
bundle. Publish a corrected bundle with a new identifier, or point `current` at
a retained compatible bundle. Never edit a published directory in place.

Watch structured `[duxt] content bundle` activation/rejection logs (id, commit,
reason). For diagnostics, optionally set `contentBundles.statusRoute: true` in
the runtime configuration. `GET /__duxt/content-bundle` reports `active`,
`compatHash`, `lastRejection` and IPX `warnings`. Protect this route at ingress or
the network boundary; it is off by default and is not a metrics endpoint.

Every replica switches independently. Budget the configured polling interval
plus validation/import and draining in-flight renders. A full browser reload
gets the new checksums and invalidates stale Content dumps; an open tab may keep
old data across SPA navigation until then. Redirects, media, MCP paths, OG and
sitemap caches follow activation. External search indexes refresh through the pack's `duxt:search:records` hook.
See [Runtime content bundles](/concepts/runtime-content-bundles) for these limits,
what still needs an image, and why transport remains the operator's task.


## Checklist

- [ ] Build both targets from the app's commit and lockfile.
- [ ] Extract the compatibility artefact from the image being targeted.
- [ ] Require `--expect` before publishing a content change.
- [ ] Transfer complete immutable directories before updating `current`.

- [ ] Configure both runtime variables and writable symlink ownership.
- [ ] Protect diagnostics and plan replica skew, browser reloads and external indexes.
