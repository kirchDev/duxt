Auto-imported, like every composable in a Nuxt layer.

## Config and content

| Composable            | Returns                                                  |
| :-------------------- | :------------------------------------------------------- |
| `useDuxtConfig()`     | The merged config, every text field already resolved to a string |
| `useDuxtCollection()` | `{ collection, source, sources }` — which collection serves this route |
| `useDuxtNavigation()` | `useAsyncData` of the navigation tree for that collection  |
| `useDuxtSection()`    | `{ section, items }` — the part of the docs this page is in |
| `useDuxtBreadcrumb()` | The trail from the section down to a page                  |

`useDuxtConfig()` is the one to reach for in a replaced component: it does the
array-replacing merge and the text resolution, so a template never meets an i18n
key or a per-locale record.

`useDuxtCollection().collection` is a **string**, not a literal type — a site's
collection names are generated from its own sources, so nothing in the layer can
name them. Pass it to `queryCollection` rather than writing `'docs'`.

## Paths and versions

| Composable          | Returns                                                              |
| :------------------ | :------------------------------------------------------------------- |
| `useDuxtPath()`     | The path the documentation is at — the locale segment stripped        |
| `useDuxtLink()`     | The inverse: a documentation path written back out as a link          |
| `useDuxtVersion()`  | `{ sources, current, preferred, isPreferred, status, kind, shouldIndex, shouldWarn, preferredPath }` |
| `useDuxtSiteUrl()`  | `{ origin, absolute }` — the configured origin, and paths made absolute |

`useDuxtVersion()` answers three questions from one place — what the switcher
shows, what the banner says, and whether the page asks to be indexed — because
they are the same question about the same version.

## Reading experience

| Composable              | Returns                                                       |
| :---------------------- | :------------------------------------------------------------ |
| `useDuxtSearch()`       | `{ search, init, labelled }` — across every source, ranked together |
| `useFuzzySearch()`      | `{ search }` — typo tolerance beside Content's own index        |
| `useActiveHeading(ids)` | The heading currently in view                                   |
| `useDuxtPageFocus()`    | Moves focus to the page's heading after a client-side navigation |
| `useRecentPages()`      | `{ recent, remember, load }` — this reader's last five pages     |
| `usePackageManager()`   | The reader's chosen package manager, as a cookie                |
| `useDuxtToast()`        | `{ success, info, warning, error, loading, dismiss }`            |
| `useDuxtShortcuts()`    | The keys the theme listens to                                   |

Two of these exist as seams rather than as conveniences. `useDuxtToast()` wraps
the toast library so no component imports it directly — a site that wants a
different notification system replaces one file. `useDuxtShortcuts()` is the one
place that knows which keys are bound, so the overlay on `?` and the handlers
cannot disagree; `onDuxtShortcut()` beside it binds one key with the guards every
binding needs, including never firing while the reader is typing.

`usePackageManager()` is a cookie rather than browser storage, and deliberately:
storage is read after hydration, so the block would render one manager and then
swap to another in front of the reader. It is first-party, identifies nobody and
carries a value the reader chose. `useRecentPages()` is the opposite case — never
needed during server rendering, so it stays in the browser and travels with no
request.
