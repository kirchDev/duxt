All of it is generated from the same collections the pages render from, so none of
it can drift from what is published.

| Path             | What it is                                                        |
| :--------------- | :---------------------------------------------------------------- |
| `/llms.txt`      | The documentation as a Markdown index, per llmstxt.org             |
| `/llms-full.txt` | The same pages, whole, in one Markdown file                        |
| `<page>.md`      | Any page's own Markdown source                                     |
| `/mcp`           | An MCP server — `list_pages`, `search_docs`, `read_page`            |
| `/sitemap.xml`   | The default version's pages, per locale                            |
| `/robots.txt`    | Generated beside the sitemap                                       |
| `/rss.xml`       | The feed — empty until `duxt.feed.path` names a section             |
| `/_duxt/devtools` | The Nuxt Devtools panel. **Dev only** — never registered in a build |

Three of them come with a caveat worth knowing:

- **`/rss.xml` answers empty rather than 404** before it is configured: a feed
  client should be told there is nothing here, not that the feed is gone.
- **`<page>.md` is a middleware, not a route**, because `.md` is a suffix on the
  last segment rather than a segment of its own.
- **`/_duxt/devtools` exposes the resolved config, the file system paths behind it
  and a button that deletes a cache directory.** None of that is anybody's
  business in production, which is why the module returns before registering
  anything outside a dev server.

The devtools panel is the answer to the part of this layer that has been hardest
to debug: what a consumer writes is a compact list, and what the site serves is a
set of collections, prefixes, redirects, message catalogues and a download cache
the build computed from it. Its panels show each of those as the running app has
them, rather than as a snapshot — sources, paths resolved step by step, pages,
which version carries which page, the build checks re-run, what the search index
holds, the merged config with the side of the merge each value came from, the
locale keys against the base, the content cache, and the redirects.

Everything a model reads, and why there are two llms files, is in
[Machine readers](/concepts/machine-readers).
