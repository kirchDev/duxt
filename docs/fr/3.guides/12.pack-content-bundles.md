Un paquet de contenu analyse les sources sans compiler Vite ni Nitro.
Construisez l'outil depuis le commit de l'application pour conserver le même
schéma, les mêmes collections et composants.
[L'ADR-0013](/adr/0013-load-content-bundles-at-runtime) précise le périmètre Node
et SQLite ; les déploiements habituels reconstruisent toujours l'application.

::callout{type="warning"}
Cette commande produit uniquement un artefact. Elle ne permet pas encore à un
serveur actif de charger ou de surveiller des bundles.
::

## Construire ensemble l'application et l'outil

`examples/content-bundles/Dockerfile` propose les cibles `app` et `packer`, avec
une étape source et un lockfile communs. Depuis la racine du dépôt :

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

La compilation écrit `.output/duxt-content-compat.json`. Extrayez ce fichier de
l'image sans démarrer le serveur ; il contient le hash de compatibilité
structurelle et les composants MDC disponibles. Pour votre site, adaptez le
répertoire de l'application et construisez les deux cibles depuis le même checkout.

## Empaqueter une modification documentaire

Modifiez le Markdown de l'exemple et montez ce répertoire dans l'outil :

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

Dans une application installée, lancez `duxt content pack` à la racine Nuxt.
La commande analyse les sources sans compilation préalable. Consultez les
options et codes de sortie avec `duxt content pack --help`. Elle affiche le
chemin du bundle et son hash. `--expect` lit l'artefact applicatif et refuse une
structure différente ou des composants absents de l'image avant publication.
Employer d'autres composants déjà disponibles ne change pas le hash structurel.

## Transférer le résultat complet

Un répertoire au format 1 porte le SHA-256 de son fichier `SHA256SUMS`. Il
contient `bundle.json` avec provenance, compatibilité et `usedComponents`, les
`checksums` de Content, ses dumps compressés inchangés dans
`dumps/<collection>.txt`, `redirects.json` et les médias documentaires dans
`media/`. Les hashes couvrent tous les fichiers utiles. La provenance indique
les versions de Content et duxt, ainsi que le commit si les métadonnées Git existent.

La publication écrit et renomme d'abord le répertoire complet, puis remplace
atomiquement le fichier UTF-8 `current` contenant son identifiant. Les deux
opérations doivent utiliser le même système de fichiers. Synchronisez les
répertoires immuables avant `current` ; le transport appartient à votre
infrastructure. Gardez les anciens répertoires tant qu'un lecteur peut les utiliser.

Le workflow `Content packer` construit les deux cibles Docker, extrait
l'artefact, modifie le Markdown et vérifie les hashes d'un paquet compatible.

## Liste de contrôle

- [ ] Construire les deux cibles avec le commit et le lockfile de l'application.
- [ ] Extraire l'artefact de compatibilité de l'image ciblée.
- [ ] Exiger `--expect` avant de publier une modification.
- [ ] Transférer les répertoires complets avant de modifier `current`.
