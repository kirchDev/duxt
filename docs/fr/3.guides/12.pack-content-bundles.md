Un paquet de contenu analyse les sources sans compiler Vite ni Nitro.
Construisez l'outil depuis le commit de l'application pour conserver le même
schéma, les mêmes collections et composants.
[L'ADR-0013](/adr/0013-load-content-bundles-at-runtime) précise le périmètre Node
et SQLite ; les déploiements habituels reconstruisent toujours l'application.

::callout{type="warning"}
Cette commande produit uniquement un artefact. Elle ne permet pas encore à un
serveur actif de charger ou de surveiller des bundles.
::

## Construire ensemble l'application et l'outil

`examples/content-bundles/Dockerfile` propose les cibles `app` et `packer`, avec
une étape source et un lockfile communs. Depuis la racine du dépôt :

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

La compilation écrit `.output/duxt-content-compat.json`. Extrayez ce fichier de
l'image sans démarrer le serveur ; il contient le hash de compatibilité
structurelle et les composants MDC disponibles. Pour votre site, adaptez le
répertoire de l'application et construisez les deux cibles depuis le même checkout.

## Empaqueter une modification documentaire

Modifiez le Markdown de l'exemple et montez ce répertoire dans l'outil :

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

Dans une application installée, lancez `duxt content pack` à la racine Nuxt.
La commande analyse les sources sans compilation préalable. Consultez les
options et codes de sortie avec `duxt content pack --help`. Elle affiche le
chemin du bundle et son hash. `--expect` lit l’artefact et refuse une structure différente ou un composant MDC
indisponible avant publication. `availableComponents` comprend les composants
`app/components/content/` du consommateur et de toutes les couches, ainsi que les
composants déjà globaux, comme ceux de prose de Content. Les composants UI/de mise
en page inutilisés hors de cet ensemble sont exclus. Un composant peut apparaître
pour la première fois dans un bundle si son code figurait déjà dans un répertoire
de contenu de l’image ; changer le sous-ensemble utilisé ne modifie pas le hash structurel.

## Historique Git et recherche

Une source qui lit l’historique exige Git, un checkout valide et l’historique
complet. Un historique absent ou superficiel arrête le pack avant publication,
même si toutes les pages sont en cache. Un build ordinaire avertit seulement.
Les sources locales lisent l’historique par défaut ; `history: false` le désactive
explicitement. Les sources distantes doivent l’activer et complètent leur clone.

L’exemple Docker choisit `history: false` : `.git` marque seulement la racine des
chemins, sans Git ni historique. Pour conserver dates et contributeurs, fournissez
Git et l’historique complet au target packer, hors du target de l’application.

Après publication, [`duxt:search:records`](/reference/hooks) synchronise le
fournisseur installé avec des clés d’écriture uniquement dans le packer.
Un échec fait échouer la commande mais conserve le bundle publié ; relancez le
pack. L’index peut précéder le contenu de `pollSeconds` plus l’importation, ou
jusqu’au prochain pack valide si le serveur rejette le bundle.

## Transférer le résultat complet

Un répertoire au format 1 porte le SHA-256 de son fichier `SHA256SUMS`. Il
contient `bundle.json` avec provenance, compatibilité et `usedComponents`, les
`checksums` de Content, ses dumps compressés inchangés dans
`dumps/<collection>.txt`, `redirects.json` et les médias documentaires dans
`media/`. Les hashes couvrent tous les fichiers utiles. La provenance indique
les versions de Content et duxt, ainsi que le commit si les métadonnées Git existent.

La publication écrit et renomme d'abord le répertoire complet, puis remplace
atomiquement le fichier UTF-8 `current` contenant son identifiant. Les deux
opérations doivent utiliser le même système de fichiers. Synchronisez les
répertoires immuables avant `current` ; le transport appartient à votre
infrastructure. Gardez les anciens répertoires tant qu'un lecteur peut les utiliser.

Le workflow `Content packer` construit les deux cibles Docker, extrait
l'artefact, modifie le Markdown et vérifie les hashes d'un paquet compatible.

## Activer le chargement à l’exécution

Construisez un serveur Node de production avec SQLite dans un fichier.
Désactivez le prérendu des pages à modifier : le HTML statique ne suit pas la
base. Avant de construire app et packer, par exemple :

```ts
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt'],
  routeRules: { '/**': { prerender: false } },
  nitro: { preset: 'node-server', prerender: { crawlLinks: false, routes: [] } },
  runtimeConfig: {
    duxt: { contentBundles: { pollSeconds: 30, statusRoute: false } },
  },
})
```

Une image construite sans variables de bundles peut les activer au démarrage.
Pour l’application Docker fournie, définissez **les deux variables avant Node** :

```sh
docker run --rm -p 3000:3000 \
  -v "$PWD/publish:/content-bundles" \
  -e DUXT_CONTENT_BUNDLE_DIR=/content-bundles \
  -e 'NUXT_IPX_FS_DIR=["/content-bundles/active/media","/app/public"]' \
  docs-app
```

`NUXT_IPX_FS_DIR` inclut `active/media` et les racines habituelles des images.
Ajoutez les autres racines de votre site ; `/app/public` correspond à ce Docker.
IPX natif reste en place. Une racine manquante produit un avertissement dans les
logs et le statut, sans empêcher l’activation d’un bundle valide.

L’application doit pouvoir créer/renommer le lien symbolique `active` dans le
volume. Ne créez pas `active` comme répertoire. Les répertoires immuables et
`current` appartiennent à l’opérateur ; duxt gère le lien. L’alternative à la
variable courte est `runtimeConfig.duxt.contentBundles.dir`. Sans répertoire,
l’application sert le contenu de son image.

## Publier, observer et restaurer

Transférez les répertoires immuables complets, puis remplacez `current`
atomiquement. Le serveur vérifie au démarrage puis interroge périodiquement ;
aucun redémarrage n’est requis. Un bundle absent ou refusé au départ laisse servir
l’image ; un refus ultérieur conserve le bundle actif. Publiez la correction sous
un nouvel identifiant ou pointez `current` vers un bundle compatible conservé.
Ne modifiez jamais un répertoire publié.

Les logs structurés `[duxt] content bundle` indiquent id, commit et raison.
L’option `contentBundles.statusRoute: true` dans la configuration d’exécution
active `GET /__duxt/content-bundle`, avec `active`, `compatHash`, `lastRejection` et
les `warnings` IPX. Protégez cette route à l’ingress ou au niveau réseau ; elle
est désactivée par défaut et ne fournit pas de métriques.

Les réplicas basculent indépendamment. Prévoyez l’intervalle d’interrogation,
la validation/import et l’attente des rendus en cours. Un rechargement complet
applique les nouveaux checksums et invalide les anciens dumps ; un onglet peut
conserver ses données en navigation SPA. Redirections, médias, chemins MCP et
caches OG/sitemap suivent l’activation. Les index externes sont actualisés par le
hook `duxt:search:records` du pack. [Bundles à l’exécution](/concepts/runtime-content-bundles) précise
ces limites, les changements nécessitant une image et le transport côté opérateur.
