Une extension duxt est une couche Nuxt. Les composants, les valeurs par défaut de
`app.config`, les routes serveur et les modules transitent déjà par `extends`. Ce que
Nuxt ne peut pas transporter, c’est tout ce que la compilation du contenu doit
savoir : quel moteur de rendu reçoit une page, comment un artefact devient des pages
et quels champs une page peut stocker. Cela se place dans un fichier nommé
`duxt.build.ts` à la racine de la couche.

[L’ADR-0014](/adr/0014-load-integration-contributions-only-at-build-time) explique
pourquoi ce fichier existe et pourquoi les analyseurs ne vont jamais dans
`app.config.ts`, qui est compilé dans le navigateur.

## Écrire le fichier

```ts [duxt.build.ts]
import type { DuxtBuildContribution } from '@kirchdev/duxt/unstable';

export default {
  pageTypes: {
    recipe: { layout: 'recipe', template: 'RecipePage' }
  },
  pageSchema: (z) => ({
    servings: z.number().optional()
  })
} satisfies DuxtBuildContribution;
```

Le fichier peut fournir quatre choses :

| Clé             | Ce qu’elle ajoute                                                   |
| :-------------- | :------------------------------------------------------------------ |
| `pageTypes`     | Une mise en page et un template, associés sous un même nom          |
| `sectionTypes`  | Un analyseur de [section générée](/concepts/generated-sections)     |
| `sourceFlavors` | Une façon de lire un dialecte Markdown existant                     |
| `pageSchema`    | Des champs de page, déclarés avec le `z` que Content passe au callback |

Chaque couche peut en fournir un. Ils sont fusionnés le long de `extends`, et le site
est prioritaire. Les maps sont remplacées par entrée : un site peut ainsi remplacer un
type de page sans redéclarer les autres.

::callout{type="warning"}
`@kirchdev/duxt/unstable` est le seul export provisoire. Son contenu peut changer
avant que la frontière d’extraction soit arrêtée : épinglez donc la version de duxt
avec laquelle une extension est construite.
::

## Ajouter un type de page

Un type de page associe une mise en page Nuxt, qui enveloppe la page, à un composant
template, qui dessine l’article. Fournissez les deux dans la couche :

```vue [app/components/RecipePage.vue]
<script setup lang="ts">
import type { DuxtPageTemplateProps } from '@duxt/utils/page-types';
defineProps<DuxtPageTemplateProps>();
</script>

<template>
  <article>
    <h1>{{ page.title }}</h1>
    <ContentRenderer :value="page" />
  </article>
</template>
```

Le nom du template doit être en PascalCase et se résoudre comme un composant global.
La route a déjà chargé la page et géré le SEO : un template reçoit donc uniquement
`page`, `untranslated` et `from`.

Sélectionnez le type pour toute une source avec `pageType`, ou pour une seule page
avec `type` dans son frontmatter. La page est prioritaire. Nommer un type que rien
n’enregistre fait échouer la compilation ou la requête au lieu de se replier sur le
template de documentation, car un repli silencieux afficherait la mauvaise page.

## Savoir ce qui exige une nouvelle image

`duxt.build.ts` s’exécute lors de la construction de l’image applicative. Ajouter un
type de page, un analyseur ou un champ est une modification de code, même sur un site
qui livre ses pages par [bundles de contenu](/concepts/runtime-content-bundles). Le
contenu qui les utilise peut ensuite transiter dans un bundle.

## Liste de contrôle

- [ ] `duxt.build.ts` se trouve à la racine de la couche et figure dans les `files` du paquet
- [ ] Aucun analyseur ni schéma n’atteint `app.config.ts`
- [ ] La mise en page et le template de chaque type de page sont livrés dans la couche
- [ ] Les champs sont déclarés avec le `z` reçu par le callback
- [ ] Le site se compile avec la couche uniquement dans `extends`
