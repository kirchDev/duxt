Les mêmes vérifications que `pnpm build`, depuis le même code — l’intérêt n’est pas
un deuxième avis, mais un endroit où les constats restent. Un avertissement affiché
pendant un build a défilé bien avant que quiconque le lise.

::devtools-panel{tab="checks"}
::

## Ce qui est vérifié

Les **erreurs** sont ce qui rend une URL injoignable :

- une **collection sans pages**, dont tout le préfixe est un 404 ;
- un **dossier nommé comme un segment de dépôt ou de version**, que le préfixe
  masque entièrement.

Les **avertissements** sont ce qui dégrade une page en silence :

- **pas de `title` ou pas de `description`** — la table des matières, les cartes,
  l’image OG et llms.txt les lisent tous ;
- un **lien vers une page que personne ne sert**, résolu exactement comme `ProseA`
  le résout au rendu : d’abord sous le préfixe de la source, ensuite nu ;
- un **lien vers une ancre que cette page n’a pas** ;
- ce qu’une **section générée** n’a pas su interpréter — un artefact absent à
  cette ref, un artefact dont le type n’a rien lu, un `$ref` irrésoluble dans un
  document OpenAPI, un titre de changelog qui ressemble à une release mais ne
  s’analyse pas comme telle.

::callout{type="tip" title="Les sections signalaient ailleurs"}
Un artefact est analysé pendant le chargement de la configuration : ce qu’un type
ne parvenait pas à lire était donc affiché bien avant qu’un serveur de
développement ait fini de démarrer — et parti quand quelqu’un regardait enfin.
Ces constats passent désormais par ce panneau, ce qui est toute la raison de son
existence. Voir
[Ce que la compilation vérifie](/concepts/build-checks).
::

## Notes

Les constats nomment leur fichier entre guillemets, et le panneau transforme le
premier en un lien qui ouvre votre éditeur à cet endroit.

Les liens sont vérifiés **en interne uniquement**. Une URL externe n’est pas à ce
build de la vérifier, et le faire mettrait le réseau dans le build.
