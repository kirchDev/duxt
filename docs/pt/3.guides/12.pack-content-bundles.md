Um pacote de conteúdo processa as fontes sem compilar Vite nem Nitro.
Cria o empacotador a partir do commit da aplicação para manter o mesmo esquema,
as coleções e os componentes. A
[ADR-0013](/adr/0013-load-content-bundles-at-runtime) explica o âmbito Node e
SQLite; os outros deployments continuam a reconstruir a aplicação.

::callout{type="warning"}
Este comando produz apenas um artefacto. Ainda não faz um servidor em execução
carregar ou vigiar bundles.
::

## Construir a aplicação e o empacotador em conjunto

`examples/content-bundles/Dockerfile` contém os targets `app` e `packer`, que
partilham uma etapa de fontes e o lockfile. Na raiz do repositório:

```sh
docker build -f examples/content-bundles/Dockerfile --target app -t docs-app .
docker build -f examples/content-bundles/Dockerfile --target packer -t docs-packer .
mkdir -p expected publish
container=$(docker create docs-app)
docker cp "$container:/app/duxt-content-compat.json" expected/compat.json
docker rm "$container"
```

A compilação escreve `.output/duxt-content-compat.json`. Extrai o ficheiro da
imagem sem iniciar o servidor; contém o hash de compatibilidade estrutural e os
componentes MDC disponíveis. Para outro site, ajusta o diretório da aplicação e
constrói os dois targets a partir do mesmo checkout.

## Empacotar uma alteração de documentação

Altera o Markdown do exemplo e monta esse diretório no empacotador:

```sh
docker run --rm \
  -v "$PWD/expected:/expected:ro" \
  -v "$PWD/publish:/publish" \
  -v "$PWD/examples/content-bundles/site/docs:/app/examples/content-bundles/site/docs:ro" \
  docs-packer --expect /expected/compat.json --publish /publish
```

Numa aplicação instalada, executa `duxt content pack` na raiz Nuxt. O comando
processa as fontes sem uma compilação anterior. Consulta as opções e os códigos
de saída com `duxt content pack --help`. Imprime o caminho do bundle e o hash.
`--expect` lê o artefacto e rejeita uma estrutura diferente ou componentes MDC
indisponíveis antes da publicação. `availableComponents` inclui componentes em
`app/components/content/` do consumidor e de todas as camadas, mais os já globais,
como os de prosa do Content. Exclui componentes UI/de disposição não utilizados
fora desse conjunto. Um componente pode aparecer pela primeira vez num bundle se
o código já existia num diretório de conteúdo da imagem; mudar o subconjunto
utilizado não altera o hash estrutural.

## Histórico Git e pesquisa

Uma fonte que lê histórico precisa de Git, de um checkout válido e do histórico
completo. Histórico ausente ou superficial impede a publicação do pack, mesmo
com todas as páginas em cache. Um build normal apenas avisa. As fontes locais
leem histórico por predefinição; `history: false` desativa-o explicitamente.
As fontes remotas têm de o ativar e completam o clone antes de o ler.

O exemplo Docker escolhe `history: false`: `.git` só marca a raiz dos caminhos,
sem Git nem histórico. Para manter datas e contribuidores, fornece Git e histórico
completo no target packer, sem metadados de checkout no target da aplicação.

Após publicar, [`duxt:search:records`](/reference/hooks) sincroniza o fornecedor
instalado com chaves de escrita apenas no packer. Se falhar, o comando falha e
o bundle continua publicado; repete o pack. O índice pode antecipar o conteúdo
por `pollSeconds` mais a importação, ou até ao próximo pack válido se o servidor
rejeitar o bundle.

## Transferir o resultado completo

Um diretório de formato 1 recebe o SHA-256 do seu ficheiro `SHA256SUMS`. Contém
`bundle.json` com proveniência, compatibilidade e `usedComponents`, os
`checksums` do Content, os dumps comprimidos inalterados em
`dumps/<collection>.txt`, `redirects.json` e os ficheiros multimédia da
documentação em `media/`. Os hashes abrangem todos os ficheiros de dados. A
proveniência inclui as versões do Content e duxt e o commit quando existem
metadados Git.

A publicação escreve e renomeia primeiro o diretório completo; depois substitui
atomicamente o ficheiro UTF-8 `current`, que contém o identificador. As duas
operações precisam do mesmo sistema de ficheiros. Sincroniza os diretórios
imutáveis antes de `current`; o transporte pertence à infraestrutura de
deployment. Mantém os diretórios antigos enquanto algum leitor os possa usar.

O workflow `Content packer` constrói os dois targets Docker, extrai o artefacto,
altera Markdown e verifica os hashes de um pacote compatível.

## Ativar o carregamento em execução

Constrói um servidor Node de produção com SQLite num ficheiro. Desativa a
pré-renderização das páginas a alterar: HTML estático não acompanha a base de
dados. Antes de construir app e packer, por exemplo:

```ts
export default defineNuxtConfig({
  extends: ['@kirchdev/duxt'],
  routeRules: { '/**': { prerender: false } },
  nitro: { preset: 'node-server', prerender: { crawlLinks: false, routes: [] } },
  runtimeConfig: {
    duxt: { contentBundles: { pollSeconds: 30, statusRoute: false } },
  },
})
```

Uma imagem construída sem variáveis de bundles pode ativá-los no arranque.
Para a aplicação Docker fornecida, define **as duas variáveis antes de Node**:

```sh
docker run --rm -p 3000:3000 \
  -v "$PWD/publish:/content-bundles" \
  -e DUXT_CONTENT_BUNDLE_DIR=/content-bundles \
  -e 'NUXT_IPX_FS_DIR=["/content-bundles/active/media","/app/public"]' \
  docs-app
```

`NUXT_IPX_FS_DIR` inclui `active/media` e as raízes habituais das imagens.
Acrescenta outras raízes do site; `/app/public` corresponde a este Docker.
Mantém-se IPX nativo. Uma raiz ausente gera aviso nos logs e no estado, mas não
impede a ativação de um bundle válido.

A aplicação precisa de criar/renomear a ligação simbólica `active` no volume.
Não cries `active` como diretório. Os diretórios imutáveis e `current` pertencem
ao operador; duxt gere a ligação. A alternativa à variável curta é
`runtimeConfig.duxt.contentBundles.dir`. Sem diretório, serve-se o conteúdo da imagem.

## Publicar, observar e recuperar

Transfere diretórios imutáveis completos e substitui `current` atomicamente no
fim. O servidor verifica no arranque e consulta periodicamente; não é preciso
reiniciar. Um bundle ausente ou inválido no início deixa servir a imagem; uma
rejeição posterior mantém o ativo. Publica a correção com outro identificador ou
aponta `current` para um bundle compatível guardado. Nunca alteres um diretório publicado.

Os logs estruturados `[duxt] content bundle` incluem id, commit e motivo.
Opcionalmente, `contentBundles.statusRoute: true` na configuração de execução
ativa `GET /__duxt/content-bundle`, com `active`, `compatHash`, `lastRejection` e
`warnings` de IPX. Protege a rota no ingress ou na rede; está desativada por
predefinição e não é um endpoint de métricas.

As réplicas mudam independentemente. Conta com o intervalo de consulta,
validação/importação e espera pelas renderizações em curso. Um recarregamento
completo aplica novos checksums e invalida dumps antigos; um separador pode manter
dados antigos na navegação SPA. Redirecionamentos, média, caminhos MCP e caches
OG/sitemap acompanham a ativação. Os índices externos são atualizados pelo hook `duxt:search:records` do pack.
[Bundles em execução](/concepts/runtime-content-bundles) explica estes limites,
quando reconstruir a imagem e o transporte a cargo do operador.
