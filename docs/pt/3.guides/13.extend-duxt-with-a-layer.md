Uma extensão do duxt é uma camada Nuxt. Componentes, valores predefinidos de
`app.config`, rotas de servidor e módulos já viajam através de `extends`. O que o
Nuxt não consegue transportar é tudo o que a compilação do conteúdo tem de saber: que
renderizador recebe uma página, como um artefacto se transforma em páginas e que
campos uma página pode guardar. Isso vai num ficheiro chamado `duxt.build.ts` na raiz
da camada.

A [ADR-0014](/adr/0014-load-integration-contributions-only-at-build-time) explica
porque existe este ficheiro e porque os analisadores nunca vão para `app.config.ts`,
que é compilado para o navegador.

## Escrever o ficheiro

```ts [duxt.build.ts]
import type { DuxtBuildContribution } from '@kirchdev/duxt/unstable';

export default {
  pageTypes: {
    recipe: { layout: 'recipe', template: 'RecipePage' }
  },
  pageSchema: (z) => ({
    servings: z.number().optional()
  })
} satisfies DuxtBuildContribution;
```

O ficheiro pode contribuir com quatro coisas:

| Chave           | O que adiciona                                                      |
| :-------------- | :------------------------------------------------------------------ |
| `pageTypes`     | Um layout e um template, associados sob um único nome               |
| `sectionTypes`  | Um analisador de [secção gerada](/concepts/generated-sections)      |
| `sourceFlavors` | Uma forma de ler um dialeto de Markdown existente                   |
| `pageSchema`    | Campos de página, declarados com o `z` que o Content passa ao callback |

Cada camada pode incluir um. São combinados ao longo de `extends` e o site tem
prioridade. Os mapas são substituídos por entrada, por isso um site pode substituir um
tipo de página sem voltar a declarar os outros.

::callout{type="warning"}
`@kirchdev/duxt/unstable` é a única exportação provisória. O seu conteúdo pode mudar
antes de a fronteira de extração ficar definida, por isso fixa a versão do duxt com
que uma extensão é construída.
::

## Adicionar um tipo de página

Um tipo de página associa um layout do Nuxt, que envolve a página, a um componente de
template, que desenha o artigo. Inclui ambos na camada:

```vue [app/components/RecipePage.vue]
<script setup lang="ts">
import type { DuxtPageTemplateProps } from '@duxt/utils/page-types';
defineProps<DuxtPageTemplateProps>();
</script>

<template>
  <article>
    <h1>{{ page.title }}</h1>
    <ContentRenderer :value="page" />
  </article>
</template>
```

O nome do template tem de estar em PascalCase e resolver-se como componente global. A
rota já carregou a página e tratou do SEO, por isso um template recebe apenas `page`,
`untranslated` e `from`.

Seleciona o tipo para toda uma fonte com `pageType`, ou para uma só página com `type`
no seu frontmatter. A página tem prioridade. Indicar um tipo que nada regista faz
falhar a compilação ou o pedido em vez de recorrer ao template de documentação,
porque um recurso silencioso mostraria a página errada.

## Saber o que exige uma nova imagem

`duxt.build.ts` é executado quando a imagem da aplicação é construída. Adicionar um
tipo de página, um analisador ou um campo é uma alteração de código, mesmo num site
que entrega as suas páginas através de
[bundles de conteúdo](/concepts/runtime-content-bundles). O conteúdo que os utiliza
pode depois viajar num bundle.

## Lista de verificação

- [ ] `duxt.build.ts` está na raiz da camada e consta dos `files` do pacote
- [ ] Nenhum analisador ou esquema chega a `app.config.ts`
- [ ] O layout e o template de cada tipo de página são incluídos na camada
- [ ] Os campos são declarados através do `z` que o callback recebe
- [ ] O site compila com a camada apenas em `extends`
